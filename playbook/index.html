When does content addressing pay?

Block pointers share what has common history. Content addressing shares what has common content. These are different sets of bytes. Nobody has measured the difference — and the difference decides which storage architecture is right.

The pitch in four sentences

  1. The storage community answers this question with folklore: "dedup is rarely worth it," "clones capture what matters," "compression gets the rest."
  2. The file-vs-block version of this question was measured for desktops in 2011, containers in 2020, and models in 2025 — VM images still rest on 2009 data, and the lineage-vs-content axis has never been measured for any domain.
  3. This study decomposes redundancy on real corpora into lineage-capturable, convergent-only, and compression-capturable bytes, then measures the runtime taxes of capturing each.
  4. Phase one is offline analysis with first numbers in two weeks; each later phase runs only if the numbers before it justify the build.

The model

Two mechanisms

Path-dependent sharing (block pointers). Sharing is descent: COW clones, backing chains, snapshots. Free at write time. Blind to convergence — two clones that upgrade to identical package versions look increasingly different to a pointer tree while their content becomes increasingly identical.

Path-independent sharing (content addressing). Sharing is identity. It captures descent and convergence both. It pays for this with hash cycles, a global index, read-modify-write below chunk size, and fragmentation.

The decomposition

Every corpus byte lands in exactly one class:

  • Llineage-capturable: an ideal clone/reflink regime with full provenance captures it.
  • Cconvergent-only: content identity finds it; no lineage regime can.
  • Zcompression-capturable: zstd removes it without either mechanism.
  • Uunique.

The headline of the paper is the measured size of C, per corpus, per granularity. If C is small everywhere, COW + zstd wins and the field should stop building block-level dedup. If C is large, chunk CAS earns its complexity. Either answer is a finding.

The cost model

Chunk CAS pays when: value(C) + value(lineage-free sync) > tax(index) + tax(hash) + tax(RMW) + tax(fragmentation).

Every term is measured, none assumed. Index tax scales with 1/chunk-size. RMW tax follows the write-size distribution against chunk size. Sync value is reconciliation bytes: content addressing syncs by set difference with no common history; lineage sync degrades to full transfer without common snapshots.

Claims and folklore

Claims

  • C1Decomposition. On real corpora, the convergent-only share C is X% — the number nobody holds. Gate V1 the decomposition accounts for 100% of corpus bytes within stated accounting error, reproducible from a committed manifest.
  • C2Crossover. The net benefit of chunk CAS crosses zero at chunk size c* per workload class, taxes included. Gate V2 the curve spans ≥ 4 granularities (4K, 16K, 64K, CDC) × ≥ 2 corpora, with error bars.
  • C3Sync. Lineage-free reconciliation transfers within ε of the true delta; lineage-based sync degrades to full transfer without common snapshots; the prolly-tree map diff is proportional to the delta while a flat-map scan is proportional to the image. Gate V3 demonstrated on ≥ 1 image pair between two hosts, bytes counted on the wire.
  • C4Runtime tax. The per-stage latency cost of content addressing under a live guest, on the casblk instrument. Gate V4 stage attribution accounts for ≥ 90% of the p99 gap against the raw-file backend.

Corpora and the lineage counterfactual

The hard methodological problem

L requires a counterfactual: what would an ideal lineage regime capture? The study operationalizes it with provenance, and pre-empts the obvious attack:

  • M1Corpora with recorded provenance (golden image + N clones, derivation graph kept) compute L exactly: bytes unchanged since the fork point.
  • M2Two lineage strengths, both reported: L-clone (declared copies only) and L-snap (copies plus full snapshot history). Critics get both counterfactuals.
  • M3Corpora with no shared provenance (independent installs, separately downloaded models) have L = 0 by construction. All redundancy found there is C or Z. This isolates pure convergence.
  • M4Compression fairness: the COW side gets stream zstd; the CAS side gets per-chunk zstd (small windows lose ratio) and dictionary mode. Both reported. An unfair compression baseline is the #1 reviewer trap; it is closed here.
  • M5Images are trimmed (fstrim) before analysis, so dead guest blocks do not count as live bytes.

L0 method

Mount images read-only. Chunk at each granularity. Hash (BLAKE3). Build per-corpus chunk sets. Intersect across images; classify against the provenance graph; decompose. A pure offline pipeline: Rust scanner, uv-run Python analysis. No VMM, no kernel work, no systems risk.

System under test (casblk v2)

Needed for C2's taxes and C4 only; L0 needs none of it. Each design position below answers a contention point, and each is testable — the open design questions are the experiment arms.

  • D1Chunking: fixed-size on the hot path, CDC offline only. Rolling-hash chunking has a throughput ceiling in front of every write, and content-defined boundaries shift, so small writes re-chunk their neighborhood. A block device delivers aligned fixed-size writes for free. CDC runs in the L0 analysis and, optionally, as a background re-chunker — post-process dedup, the architecture the discourse asks for.
  • D2Hashing: async by default. Ack after the WAL append; hash and dedup behind it. Inline hashing is an arm, not the default. This pair is the F6 experiment.
  • D3Map: flat array on the hot path; the prolly tree is a derived view. The hot path writes a flat mmap'd block map. The prolly tree is built at snapshot/sync time, deterministically, from map contents. Hot path stays simple; sync gets path-independent trees; the metadata write-amplification of a tree on the hot path never occurs. Dolt makes the tree the store; casblk makes it the view.
  • D4Index: RAM at semester scale. Bytes/TB is measured and extrapolated to answer F10. A flash-resident index is a stretch arm, never a dependency.
  • D5IO: io_uring; O_DIRECT on latency arms. The page cache is a confound for stage attribution, so latency arms run O_DIRECT; cache-sharing arms run buffered. Each experiment states its mode.
  • D6Store layout (unchanged from v1): append-only chunk log, rebuildable index, hole-punch reclamation, mark-and-sweep from block-map roots, no refcounts.
  • D7Zero chunk and discard (unchanged): WRITE_ZEROES maps to the zero chunk; DISCARD unmaps; the guest's trim is the deallocation signal.
  • D8nvme-tcp: out. Local NVMe only. C3's sync is an application-level chunk protocol; its metric is bytes, not latency. A CAS served as an NVMe-oF/TCP target with per-stage latency through the network stack is the follow-on project.

Non-goals

Encryption × dedup (chunk-size side channels and convergent-encryption probing are real; cited and excluded). Multi-host placement (CRUSH-style, future work). Production hardening.
